# Investigation Contract (Step 12A)

## 1. Purpose and scope

This document defines the Step 12A domain contract for AI-driven security investigation. Step 12A provides the structural vocabulary that a future investigation engine will use to express its conclusions: the objects in which findings, supporting evidence, and contextual observations are represented, and the constraints that keep those objects honest, deterministic, and safe.

Step 12A defines the investigation domain contract; it does not investigate, infer, persist, expose, or act on security events.

Investigation (generating findings, summarizing timelines, producing conclusions) is out of scope. The contract only *carries* the output of investigation. It contains no AI, LLM, Ollama, LangChain/LangGraph, embedding/vector, prompt, or model-call logic; no persistence; no API routes; no Kafka integration; and no agent, context builder, incident, MITRE, alerting, or response logic. Those layers are future phases and must not leak into this module.

The single most important invariant of the contract:

AI-generated inference must never be represented as observed telemetry.

## 2. Definitions and reading guide

- **Investigation Result** — a complete declaration of an investigation's outcome: what was concluded (findings), what it was concluded from (evidence), and what context was recorded (observations). One result per investigation (`investigation_id`).
- **Finding** — a conclusion produced by an investigation engine. Findings are always generated; they are never observed.
- **Evidence** — a reference to a concrete, previously-produced data object (an event, a detection, a correlation, or a risk assessment). Evidence is always source-backed; it is never generated by the investigation engine.
- **Observation** — a declared contextual statement about the investigation, its environment, or its inputs. Observations carry an explicit provenance so that AI-generated context is never mistaken for observed telemetry.
- **Provenance** — the origin classification of a piece of data. This contract introduces `AI_GENERATED` as a provenance value.

## 3. Provenance enumerations

The existing `Provenance` enum in `backend/app/schemas/security_event.py` previously contained six members:

| Member | String value | Meaning |
| --- | --- | --- |
| `OBSERVED` | `"observed"` | Raw observed telemetry (security events) |
| `ENRICHED` | `"enriched"` | Observation enriched with data from an enrichment source |
| `RECONSTRUCTED` | `"reconstructed"` | Reconstructed/backfilled event data |
| `DETECTED` | `"detected"` | Output of a detection rule or YARA match |
| `CORRELATED` | `"correlated"` | Output of the correlation agent |
| `RISK_ASSESSED` | `"risk_assessed"` | Output of the risk assessment engine |

Step 12A adds **one** member, additively, without changing any existing member or behavior:

| Member | String value | Meaning |
| --- | --- | --- |
| `AI_GENERATED` | `"ai_generated"` | Output of an AI investigation engine (findings, generated context) |

`AI_GENERATED` rounds out the provenance axis: telemetry and derived objects live at `OBSERVED` through `RISK_ASSESSED`, and AI-produced conclusions live at `AI_GENERATED`. Adding the member is backward compatible (no exhaustive member-set assertions exist downstream) and is required so that generated content can never be labeled as observed.

## 4. Pinning rules for provenance

The provenance value is not a free choice on every object. The contract encodes the semantic boundary directly:

- **`InvestigationResult.provenance` is pinned to `AI_GENERATED`.** A result is a declaration of what the investigation concluded; it can never be a piece of observed telemetry.
- **`InvestigationFinding.provenance` is pinned to `AI_GENERATED`.** A finding is a conclusion, i.e. the output of an investigation engine. The pin is the concrete enforcement of "AI-generated inference must never be represented as observed telemetry": there is no way to construct a finding that claims to be observed.
- **`InvestigationEvidence` forbids `AI_GENERATED`.** Evidence references a previously-produced data object. Passing `Provenance.AI_GENERATED` for evidence is a `ValidationError`.
- **`InvestigationObservation.provenance` is required and chosen explicitly.** Observations intentionally accept any provenance, including `AI_GENERATED`, because observations may describe either observed context or generated context. The calling layer must state which.

Any attempt to construct a result or finding with a non-`AI_GENERATED` provenance, or evidence with `AI_GENERATED` provenance, is rejected at validation time.

## 5. Evidence and coherent source references

Evidence records what the investigation is based on. To keep evidence truthful, every piece of evidence must carry a provenance *and* a reference matched to that provenance:

| Evidence provenance | Required reference field |
| --- | --- |
| `OBSERVED` | `event_id` |
| `ENRICHED` | `event_id` |
| `RECONSTRUCTED` | `event_id` |
| `DETECTED` | `detection_id` |
| `CORRELATED` | `correlation_id` |
| `RISK_ASSESSED` | `risk_assessment_id` |
| `AI_GENERATED` | (forbidden — no evidence may be AI-generated) |

Enforcement details:

- A reference field is **required and non-null** when it is the matched reference for the evidence's provenance, and must be a valid UUID.
- A reference field that is not matched to the provenance (e.g. a `correlation_id` on `OBSERVED` evidence) is **rejected**, not silently dropped. This prevents accidental mixing of provenance layers in a single evidence item.
- Mutually exclusive reference fields are not merged: one evidence item carries one provenance and one matched reference.

There is no dedicated threat-intelligence reference in the contract. The TI contract's `ExtractedIndicator` carries an indicator value and type but no domain-object ID, so there is nothing to reference; TI-derived context flows in as `ENRICHED` evidence whose `event_id` refers to the enriched event. No invented IDs are introduced.

## 6. Result structure

`InvestigationResult` mirrors the shape of risk and detection contracts while adding investigation-specific fields:

| Field | Type | Notes |
| --- | --- | --- |
| `investigation_id` | UUID | Immutable per result; default random, supplied for deterministic tests |
| `correlation_id` | UUID | Correlation that triggered the investigation (optional) |
| `risk_assessment_id` | UUID | Risk assessment that triggered the investigation (optional) |
| `confidence` | float `[0, 1]` | Investigation confidence; independent of the risk score |
| `findings` | list of Finding | Ordered, never sorted or deduplicated |
| `evidence` | list of Evidence | Ordered, never sorted or deduplicated |
| `observations` | list of Observation | Ordered, never sorted or deduplicated |
| `metadata` | dict (JSON-compatible) | Defaults to `{}` |
| `timestamp` | timezone-aware datetime | Required |
| `provenance` | `AI_GENERATED` | Pinned |

A result stands alone: every field required by the contract must be present before construction completes.

## 7. Finding and evidence reference resolution

A finding cites its supporting evidence through `evidence_ids`, a list of UUIDs matching `evidence_id` values present in the result's `evidence` list:

- Every `evidence_id` on every finding must resolve to an `evidence_id` in the result's evidence; a dangling reference is a `ValidationError` raised at result construction.
- The same evidence may be cited by multiple findings and multiple times within one finding; references are preserved as given (no deduplication).
- An empty `evidence_ids` list is allowed: a finding may be declared without citing evidence.
- Findings reference evidence; they never embed evidence objects. There is no `evidence` field on `InvestigationFinding`.

## 8. Field-level validation

- **Strings** (`finding_type`, `title`, `summary`, `evidence_type`, `observation_type`, `observation_text`): required where the contract says required, non-blank, and stripped of surrounding whitespace. Blank (`""` or whitespace-only) values are rejected.
- **Confidence** (`InvestigationResult.confidence`, `InvestigationFinding.confidence`): float, inclusive range `[0, 1]`. Confidence is a statement about how sure the conclusion is; it is deliberately **not** derived from the risk score or any other number, and it is not computed anywhere in this module.
- **Timestamps**: naive (no timezone) datetimes are rejected; a timezone-aware datetime is required.
- **Metadata**: JSON-compatible (all nested values must survive `json.dumps`), deeply validated, clones on read, defaults to `{}`. Cyclic or otherwise non-JSON metadata is rejected across results, findings, evidence, and observations.
- **Unknown fields**: mirrored behavior from risk/detection contracts (default Pydantic configuration, no `extra` allowed). Extra input fields are ignored, never stored; callers that rely on dropped fields will not observe them in `model_dump`.

## 9. Secret safety

Secret-shaped or credential-shaped content is rejected under the same policy the risk and detection contracts enforce. The policy scans key names during validation for the tokens `api_key`, `authorization`, `bearer`, and `secret` (case-insensitive), on:

- `metadata` on results, findings, evidence, and observations (recursively through nested dicts);
- `title`, `summary`, and `finding_type` on findings;
- `evidence_type` on evidence;
- `observation_type` and `observation_text` on observations.

A key named `api_key`, an `Authorization` header value, a Bearer token, a client secret, a JWT under a matching key, or a database connection string under a `secret`-shaped key is rejected at construction. The contract never logs, prints, or persists values; it only refuses to carry them.

## 10. Determinism and immutability

- **Deterministic serialization**: given identical inputs, `model_dump_json()` produces byte-identical output, including a supplied `investigation_id`. There are no non-deterministic components in serialized output.
- **No reordering**: lists are never sorted and never deduplicated; input order is authoritative.
- **Immutable inputs**: constructors never alias caller-owned mutable structures. Mutating a dict or list after construction does not change the model; the model retains a deep clone.
- **Value equality**: two models compare equal when their serialized values compare equal.

## 11. Metadata and additional data

`metadata` is the designated escape hatch for non-contractual detail. It is a free-form JSON object (see validation rules in section 8), is part of the JSON-safe and secret-safe envelope, and is deeply cloned. Metadata is never used to smuggle provenance: provenance is a first-class field on every object, and secret or non-JSON content is rejected regardless of depth.

## 12. Constructed examples

```python
from datetime import datetime, timezone

from app.schemas import (
    InvestigationEvidence,
    InvestigationFinding,
    InvestigationObservation,
    InvestigationResult,
)
from app.schemas.security_event import Provenance

ts = datetime(2026, 5, 1, 12, 0, 0, tzinfo=timezone.utc)

result = InvestigationResult(
    correlation_id=uuid4(),
    confidence=0.82,
    evidence=[
        InvestigationEvidence(
            evidence_type="detection_match",
            provenance=Provenance.DETECTED,
            detection_id=uuid4(),
        ),
        InvestigationEvidence(
            evidence_type="enriched_event",
            provenance=Provenance.ENRICHED,
            event_id=uuid4(),
        ),
    ],
    findings=[
        InvestigationFinding(
            finding_type="repeat_offender",
            title="Repeated beaconing",
            summary="Multiple windows of identical beaconing to a single controller.",
            confidence=0.82,
            evidence_ids=[detection_evidence.evidence_id],
            metadata={"windows": 3},
        ),
    ],
    observations=[
        InvestigationObservation(
            observation_type="context_summary",
            observation_text="All activity is confined to the east region.",
            provenance=Provenance.AI_GENERATED,
        ),
    ],
    timestamp=ts,
)
```

The finding is pinned `AI_GENERATED`; the evidence items are pinned to their source provenances; the observation declares its provenance explicitly; and every `evidence_ids` entry resolves.

## 13. Module structure and dependency policy

```
backend/app/schemas/investigation.py   contract module (747 lines)
backend/tests/unit/test_investigation_contract.py   contract tests (204)
backend/app/schemas/__init__.py        public re-exports
docs/development/investigation_contract.md          this document
```

The contract module imports only the Python standard library (`json`, `uuid`, `datetime`), Pydantic, and `Provenance` from `app.schemas.security_event`. It has no dependency on FastAPI, SQLAlchemy, Kafka, Redis, OpenSearch, Qdrant, HTTP clients, or any AI framework, and it must never acquire one.

## 14. Consistency with earlier contracts

- Provenance values introduced by detection (`DETECTED`), correlation (`CORRELATED`), and risk (`RISK_ASSESSED`) are unchanged, and the addition of `AI_GENERATED` does not weaken their enforcement.
- The risk assessment still requires `RISK_ASSESSED`; the correlation result still requires `CORRELATED`; both still reject `AI_GENERATED`.
- The secret-safety policy, JSON-compatibility checks, unknown-field behavior, and Pydantic version (2.x) mirror the risk contract at `backend/app/schemas/risk.py`.

## 15. Boundaries and non-goals

- No inference, generation, summarization, or reasoning logic of any kind.
- No persistence models, repositories, query layers, or database schema. Alembic is untouched; the migration head remains `4a6c8d0e1f2a`.
- No API routes, serializers for transport, or FastAPI exposure.
- No Kafka producers/consumers, no incident or MITRE representation, no alerting or response actions.
- No agent, context builder, prompt, embedding, vector store, or model client types.
- No computation of confidence from risk scores or other inputs.
